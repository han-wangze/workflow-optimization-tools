# 工作流程优化脚本

**项目状态：可运行。** 三个脚本彼此独立，读用户自备的输入文件；仓库不含原始榜单与问卷数据。

## 项目简介

手游市场研究里有三类反复出现、流程固定的手工活：从 Sensor Tower 导出里挑出本周上新的产品、翻 B 站游戏 UP 主的投稿找新游线索、把一轮轮概念测试问卷按同一套口径统计。三件事都不复杂，但每周重复、容易抄错，多轮之间的口径还要求完全一致。

这个仓库把它们写成三个独立脚本，每个只有一个入口文件、一个输入目录和一个输出文件。业务逻辑与统计口径按实际使用时的规则固定下来，路径、UP 主 UID 与品类名都换成脱敏占位值。

## 核心功能

| 脚本 | 解决什么 | 输入 → 输出 |
|---|---|---|
| `new_release_scanner.py` | Sensor Tower 免费榜的新品扫描 | 榜单导出 csv × N → 本周新增新品清单 + 更新后的去重表 |
| `bilibili_crawler.py` | 按 UID 与日期区间抓取游戏 UP 主投稿，供人工筛新游 | UP 主 UID 列表 → 投稿标题 / 链接 / 时间 csv |
| `concept_test_stats.py` | 多轮概念测试问卷的批量清洗与统计 | 问卷 Excel × N → 各品类指标表 + 批量汇总表 |

## 1. new_release_scanner.py — 新品扫描

**为什么需要**：每周要从 Sensor Tower 的 App Store 免费榜（top free）里筛出当年新上线的新品。人工比对历史名单重复且易错，而且榜单导出格式有两种，列名不一样。

**怎么做**

- **格式自适应**：榜单有两种导出格式（`Downloads` / `Revenue ($)` 一族，与 `iPhone downloads` / `iPhone revenue ($)` 一族），自动识别并映射成统一字段。
- **筛选口径**：榜单为免费榜、上线年份为目标年、且「排名变化含 new 或 排名 + 排名变化 > 100」——最后一条用来识别当期新进入免费榜前100的产品。
- **去重与回写**：读入累积的已扫描产品去重表（仅 `app name` 一列），剔掉已收录过的，剩下的就是本周新增；再把新增产品追加回去重表，并做一次空记录清理。**去重只按产品名称**：同名不同产品会被误合并，改名或本地化的产品会被重复收录。改成按 `Unified ID` 需要先给历史去重表补 ID 列（数据迁移），暂未做。
- **模块拆分**：识别格式、筛选、去重、回写各自独立成方法，改一处不影响其他处。

**运行**

```bash
# 先建好目录并放入数据
mkdir -p data/export
#   data/export/          ← 放 Sensor Tower 导出的榜单 csv（tab 分隔、utf-16）
#   data/scanned_apps.xlsx ← 已扫描产品去重表，需含 app name 列
python new_release_scanner.py
```

输出：`data/export/ST_new_games_<时间戳>.xlsx`（本周新增）与 `data/export/scanned_apps_updated.xlsx`（更新后的去重表）。

> 注：筛选年份在 `apply_filters()` 里写死为目标年份，换年份后需要改这一行。

## 2. bilibili_crawler.py — B 站内容抓取

**为什么需要**：新品扫描要看 B 站游戏 UP 主最近发了哪些投稿，再人工判断其中哪些和新游有关。手动翻投稿效率较低。

**怎么做**

- 用第三方库 `bilibili-api-python`（社区维护，非 B 站官方）**异步**抓取标题 / 链接 / 发布时间。该库只负责调接口，网络客户端要另装 aiohttp / httpx / curl_cffi 之一，见「依赖」。
- **日期先解析再比较**：`parse_date()` 把 `YYYY-MM-DD` 字符串转成 `datetime` 后再和投稿时间比，避免字符串直接比较出错。
- **显式分页 + 倒序提前退出**：`get_videos(pn=..., ps=30)` 逐页取。该方法签名是 `pn`（页码）/ `ps`（每页数），不传 `pn` 只会反复拿第一页；投稿按发布时间倒序返回，一旦翻到早于起始时间的投稿就立刻停，不做无谓翻页；不足一页也直接结束。`END_DATE` 按「包含当天」处理，比较时用左闭右开区间（`start <= pub_date < end + 1 天`）。

**运行**

```bash
# 先改脚本顶部的 UP_UIDS / START_DATE / END_DATE
pip install -r requirements-bilibili.txt
python bilibili_crawler.py
```

输出：脚本所在目录下的 `bilibili_videos.csv`（UTF-8-BOM，Excel 直接可读）。

> 抓公开投稿不需要登录；`CREDENTIAL` 默认三项留空，只有需要访问受限内容时才把浏览器 Cookie 填进去——**不要把它提交进版本库**。

## 3. concept_test_stats.py — 概念测试问卷批处理

**为什么需要**：概念测试每轮会回收一批问卷 Excel，每轮都要清洗、并按同一套口径算下载意愿 / 尖叫度 / 游玩时长。

**怎么做**

- **列名自适应**：用「固定题号前缀 + 关键词」和正则自动识别「游玩时长列」「已填写字段」「品类问题列」，问卷系统更新通常不用改代码。
- **口径严格固定**：
  - **样本量** = 「有出于爱好体验过」的用户 ∪ 「整体愿意但未选具体试玩意愿」的用户，按序号去重；
  - **整体下载意愿** = 「愿意试玩」人数 ÷ 样本量；
  - **尖叫度** 只在「愿意试玩」这个子集内取均值（排除未作答的）；
  - **游玩时长占比** 的分母是**「已填写」字段为正向值的样本数**，而不是总样本数——否则未填答的人会被错算成「不打算长玩」；
  - 男 / 女性指标用各自的子样本量分别做分母；
  - 愿意 / 不愿意下载的原因占比分别以「愿意试玩」和「不愿意试玩」人数为分母。
- **异常不中断，但会被记录**：单个文件失败、或单个品类统计出错时，都会把失败原因写进汇总表的「统计状态」并继续跑，最后输出成功 / 失败计数；品类列识别不到时直接报错并写明原因，不套用示例映射。要留神的是「未识别到『已填写』字段」这一种：游玩时长占比会按 0% 输出、只在日志里提示，该品类的状态仍记为成功——看到 0% 要回头核对列名。

**运行**

```bash
#   data/questionnaires/  ← 放待处理的问卷 Excel（每份一个文件）
python concept_test_stats.py
```

输出到 `output/`：每份问卷一份 `<文件名>_统计结果.xlsx`（含「统计结果」与「原始数据」两个页签），外加一份合并所有轮次的 `批量处理汇总表.xlsx`。

> 换一版问卷时，如果游玩时长列的题号前缀或题材关键词变了，改脚本顶部 `DURATION_COL_PREFIX` / `DURATION_COL_THEME_KEYWORDS` 两个常量即可。

## 技术栈

| 技术 | 用途 |
|---|---|
| Python 3 | 三个脚本的运行环境 |
| pandas | 榜单 csv 与问卷 Excel 的读取、清洗、分组计算 |
| openpyxl | 写出 xlsx 清单与统计表 |

```bash
pip install -r requirements.txt            # 三个脚本的公共依赖
pip install -r requirements-bilibili.txt   # 跑 bilibili_crawler.py 时改用这个
```

## 数据限制与已知问题

1. **仓库不含原始数据。** 榜单导出、B 站投稿与问卷 Excel 都不随仓库分发，换成自己的数据要先按各脚本说明准备目录与列名。
2. **新品扫描的目标年份写死在代码里**（当前为 2025，`new_release_scanner.py` 的 `apply_filters()`）；跨年使用时必须手动改，否则会返回空结果。
3. **去重只按产品名称。** 同名不同产品会被误合并，改名或本地化的产品会被重复收录。改成按 `Unified ID` 需要先给历史去重表补 ID 列，暂未做。
4. **B 站脚本不判断投稿是否与新游相关**，只按 UID 与日期区间抓取，输出后仍需人工筛。
5. **问卷统计的 0% 有两种来源**：真的没人选，或「已填写」字段没识别到。后者只在日志里提示，汇总表状态仍记成功，看到 0% 需核对列名（见上文第 3 节）。
6. **问卷输出含「原始数据」页**，可能包含个人信息，只在获授权的本地环境处理，不要提交进仓库。
7. **只在 Windows 单机、单一问卷系统的导出格式上跑过**；换问卷系统需重新核对题号前缀与关键词。

## 关于示例值

仓库代码中的路径、UP 主 UID 与题材 / 品类名（`概念A` / `概念B` / `概念C`）都是脱敏后的占位示例值，替换成实际值即可运行，业务逻辑与统计口径完整保留。代码不含任何公司内部数据、产品指标或未公开结论。
